# Decisions

## Decided
- D-01 Name: SupplySure.
- D-02 Channels: Discord bot for intake/approvals plus web app for reading. Discord first.
- D-04 Voice STT/TTS, translation, document reading: Sarvam (behind adapters).
- D-06 Stack: Python 3.12, FastAPI, Postgres (SQLite local/tests), discord.py, pydantic v2, pytest, ruff.
- D-07 Autonomy level 1: drafts only, owner approves every outbound message.
- D-08 Code computes dates and numbers; LLM extracts and explains.
- D-09 Every promise needs a verbatim, verified source quote.

## M0 choices (made while building the skeleton)
- D-14 Python: requires-python >=3.12 in pyproject. The sandbox only had 3.13, so the venv runs 3.13. Code uses nothing 3.13-specific.
- D-15 Process settings (dye slots, dye days, shift multiplier, dispatch/transit days) are not in DATA_MODEL. They stay in `data/sample/process.json` and are read by the planner in M1. Only machines and planned downtime are persisted in M0.
- D-16 Materials: ids are the item names from `orders.json` (e.g. `cotton_yarn_kg`). Stock and MOQ come from the first order that lists the material. Unit is the name suffix. `qty_per_pair = need / pairs`. `expected_arrival` is the order's `yarn_arrival`, applied only to materials from yarn suppliers.
- D-17 Seed is idempotent through `session.merge`. Machine ids are `machine-<step>`, downtime ids are `downtime-<step>-<from>`.
- D-18 Tests use a per-test SQLite file. The `/health` lifespan creates the schema on startup, so the app runs without a manual migration step.

## M1 choices (planner)
- D-19 Planner works on integer day ordinals internally (`date.toordinal()`) and returns `date` objects. Capacity rounds half up, as JS `Math.round` does.
- D-20 Planned downtime comes from `process.json` and always applies. `Flags.extra_downtime` is added on top.
- D-21 Priority: booked orders in input order, then tentative ones. `new_request_ahead` (golden flag `new_request_ahead_of_SO_1190`) generalises to "tentative orders go in front of the second booked order". For the sample that gives SO-1182, SO-1195, SO-1190.
- D-22 Netting takes `waste_pct` as a percentage (DATA_MODEL column), so `need = ceil(pairs x qty_per_pair x (1 + waste_pct/100))`. Values are rounded to 6 decimals before `ceil` to absorb float noise.
- D-23 The prototype's 400-day loop guard is kept, so an order with no capacity cannot loop forever.

## M2 choices (intake)
- D-24 The extraction schema has no date field. The model returns material, quantity, a verbatim quote, an `ambiguous` hint and a clarification question. Code parses the date out of the verified quote (`app/intake/dates.py`), so the model can't introduce a date that isn't in the message.
- D-25 Promise status is decided in code: `needs_clarification` if the model says ambiguous, the quote holds more than one distinct date, or it holds no date. The clarification question comes from the model, with a code template as fallback. It is a draft, never sent.
- D-26 Date rules (reference = `received_at` date): weekday means the next occurrence, and the same weekday means next week's (so "next Friday" equals "Friday"). An ordinal ("22nd") is the next date on or after the reference with that day. Day and month without a year is the next occurrence. "next week" is Saturday of next week (a conservative reading for a Mon-Sat factory). "today", "tomorrow", "day after tomorrow" and "in N days" are what they say. `dd/mm` is read day-first.
- D-27 Quote check: exact, case-sensitive substring of `raw_text`, `transcript` or `english_text`. For voice, the English translation counts as a source.
- D-28 Grounding checks beyond the quote: the material must be one this supplier supplies, or the promise is rejected. A quantity that doesn't appear as a number in the quote is dropped and logged.
- D-29 Injection: a regex screen runs before the model. A hit means the model is not called and no promises are created. The message is stored and `suspicious_message` is logged for the owner. A model `suspicious=true` flag has the same effect. A real promise sharing a message with hostile text is therefore dropped until the owner reviews it.
- D-30 Idempotency: the message and its promises commit in one transaction. The message id is `msg-<source>-<source_message_id>`, plus the unique constraint. A duplicate, even one lost in a race, returns `duplicate=True` and logs `duplicate_message_ignored`. Promise ids are `<message_id>-p<n>`.
- D-31 Order link: a promise links to an order only when exactly one order needs that material. Otherwise `order_id` stays null.
- D-32 `get_llm()` supports only `LLM_PROVIDER=fake` until D-03 is decided.

## M5 choices (web app)
- D-34 Milestone order: M3 (Discord) and M4 (voice) are parked at the owner's request, and M5 was built next. M5 depends only on M0 to M2.
- D-35 `orders.yarn_arrival` column added (DATA_MODEL updated). Without it, SO-1190 and SO-1195 had no yarn date, because only SO-1182 has material lines.
- D-36 Plan inputs: machines and downtime come from the DB, and dye slots and fixed durations from `process.json` (D-15). Orders are sorted by `(priority, id)` before the booked/tentative rule (D-21). The latest open promise (by `received_at`) for a material whose id contains "yarn", linked to that order, replaces `yarn_arrival` (PLANNER_SPEC "Using promises"). `use_promises=false` turns this off.
- D-37 The web app is read-only: every `/api` route is GET (tested). The browser only formats and draws. Plan, capacity per day, verdicts, netting, risk notes, graph and traversals are all computed in Python. What-if settings are query parameters, and in the browser they live in the URL hash (`#/plan?yd=2&ss=1&nra=1&kd=1`), so a scenario can be linked. Nothing is stored.
- D-38 Verdict bands follow the prototype: slack >= 2 Feasible, 0 to 1 Feasible tight, < 0 Not feasible.
- D-39 Factory Brain is derived from the tables: supplier supplies material, material is needed by order, machine steps chain to packing, packing makes order, order is for buyer, downtime affects step, plus `graph_edges` rows. Rings: order by verdict; supplier warn if a promise needs clarification, risk if a yarn promise is later than planned; material warn if its supplier is single-source; machine warn if it has downtime.
- D-40 `scripts/sample_messages.py` replays `messages.json` through the real intake pipeline with the fixture-backed FakeLLM, so the ledger has demo data while D-03 is open. The evals use the same fake.
- D-41 All server text is HTML-escaped in the browser. Supplier quotes are untrusted.

## Machines and Production plan modules
- D-42 Planner generalised: the route is the order of `Process.steps` (any number of steps, any ids). A step can have several machine groups, each with its own count and rate. Downtime can name one machine group, or a whole step, in which case machines are taken from the groups in order. Second shift applies to steps marked `second_shift` (`from_dict` defaults it to knitting only). With the sample data the output is unchanged: the golden tests pass unmodified, and a test checks that splitting knitting into two equal-rate groups gives the identical plan.
- D-43 The route, machine groups, downtime and outside-stage settings live in the DB (`process_steps`, `machines`, `downtime.machine_id/reason`, `production_settings`). This replaces D-15: `process.json` is now seed data only. No migrations yet, so after a schema change delete `supplysure.db` and seed again.
- D-44 Machine load: the planner schedules per step. A step's daily work is attributed to its machine groups in proportion to each group's capacity that day (`split_by_group`). Load % is work divided by capacity after downtime, over the plan window (first in-house work day to last finishing day). "Orders running then" for a downtime window means orders with work on that machine group during it. "Output lost" is machines out × rate × days.
- D-45 Writes from the web are limited to factory setup: `/api/machines`, `/api/downtime`, `/api/process/*`. Each is validated with pydantic and logged in `action_log` with actor `owner`. A test checks that every other `/api` route is GET only. Deleting a step that still has machines is refused (409); deleting a machine group also deletes its downtime.
- D-46 Factory Brain now has separate **machine** and **process step** nodes: machine works on step, step leads to the next step, last step makes order, downtime affects the machine group. Machine ring: warn at 85% load or if it has downtime, risk at 95%. Step ring: warn if it is the plant's limit, risk if it has no machines.
- D-47 Probable breakdowns (`planned = false`) count in the base plan like planned downtime, which is the conservative reading. Remove one in Machines to see the plan without it. A separate what-if toggle for probable downtime is not built yet.
- D-48 A route with a step that has no machines doesn't crash. The plan comes back empty with a `problems` message, and every view shows it. The scenario presets skip themselves if the step they refer to has been removed.

## SupplyGPT input layer
- D-49 Sarvam API, as documented on 2026-11-22. Speech-to-text: `POST /speech-to-text`, multipart, `model=saaras:v4`, `mode=transcribe`; `language_code` omitted means auto-detect; at most 30 s per request. Translate: `POST /translate`, `mayura:v1`, `source_language_code=auto`, at most 1,000 characters per call (longer text is split at sentence ends). Chat: `POST /v1/chat/completions`, `sarvam-105b`, `reasoning_effort=low`, `max_tokens=4096` (reasoning tokens count against it), strict `json_schema`. Auth is the `api-subscription-key` header. All calls go through `app/providers/sarvam.py`; `FakeSarvam` stands in for tests. Request shapes are tested against a mock transport.
- D-50 SupplyGPT is the owner's input layer. Text or voice (any listed Indian language) goes through Sarvam speech-to-text, then Sarvam translate (if not English), then the Sarvam LLM. The model reads the English text plus a snapshot of the factory and *proposes* actions: add machines, change a machine group, add downtime, add a step, record a supplier update. The model has no tools. Proposals wait for the owner. Approve runs the same handlers as the Machines and Production plan screens. A supplier update goes through the normal intake pipeline (source `supplygpt`), so it gets the same quote check, date rules and idempotency.
- D-51 SupplyGPT safety. Every proposal needs a verbatim quote of the owner's words (case-insensitive match, stored with the owner's casing). Every number must appear in that quote; simple number words like "two" or "a dozen" count. The model never gives dates: it copies the date words, and code resolves them against `SUPPLYSURE_TODAY`. "to Thursday" counts from the start date. An unclear date, missing number or unknown machine becomes a question, never a guess. Malformed or unknown action types are dropped and counted in the log. Apply is claimed with a conditional update, so a double click cannot apply twice; a failed apply goes back to pending with the reason.
- D-52 Text in a non-Latin script is translated even without a language hint. Latin-script text, including romanised Tamil, goes to the model as is. Replies are translated back into the owner's language and shown with the English.
- D-53 Voice is recorded in the browser with MediaRecorder and converted to 16 kHz mono WAV (Sarvam's preferred format), falling back to the browser's own format if decoding fails. Recording stops at 29 s. Uploads are capped at 10 MB and limited to audio content types.
- D-54 `SUPPLYSURE_TODAY` (in `.env`, default the real date) sets the factory's "today", because the sample data lives in June 2027. `.env` is loaded by `app/config.py` without overriding the real environment.
- D-55 SupplyGPT writes only its own tables and, on approval, factory setup or the ledger through existing code paths. The read-only test now reads the OpenAPI document: FastAPI 0.165 wraps included routers, so `app.routes` had been hiding them. That made the earlier M5 check vacuous; it is fixed, and the fix is proven by adding a forbidden route.

- D-56 Live findings with the key (2026-11-22). Measured with 4-5 runs per message: strict `json_schema` output with reasoning on produced actions in about 1 run in 5, sometimes with invalid JSON. Function calling with `reasoning_effort` off was 16 of 16 (add machines, downtime, supplier update, and a plain answer to a question). SupplyGPT therefore proposes actions through function calls; the functions are never executed, only read as proposals and validated. Reasoning is off on every chat call. The model sometimes sends `"null"` as a string, so placeholder strings count as missing.
- D-57 Supplier-message intake on Sarvam also uses function calls (`record_promise`, `flag_suspicious`), because strict-JSON mode failed in 2 of 3 live runs even with a retry. `chat_json` still retries once on malformed output. If the model call fails, intake rolls back and stores nothing, so a redelivery is processed instead of being treated as a duplicate. Live result over 3 runs: the labels promise was found 2 of 3 times (45,000 pcs, Jun 18), the third returned nothing (a miss, not a wrong promise), and the hostile message was blocked 3 of 3.
- D-58 Known translation weakness: Sarvam translate rendered "பின்னல் இயந்திரங்கள்" (knitting machines) as "sewing" or "embroidery" machines. The model now also gets the owner's original words and maps them correctly most of the time; otherwise it asks. Proposals still quote the English, so the owner sees what was understood before approving.

- D-59 Schema drift fix. The auto-reloading dev server created the SupplyGPT tables in `supplysure.db` mid-build, before a column was renamed (`error` to `reply_local`), and `create_all` never alters an existing table, so SupplyGPT history returned 500. The column was renamed in place (the tables were empty; backup in `/tmp/supplysure-backup-before-fix.db`). `create_schema` now also adds missing nullable columns to existing tables on startup (tested). Renames and type or NOT NULL changes still need a fresh database or a real migration tool (e.g. Alembic) before Postgres or hosting.

- D-60 Orders are the owner's data, so they can be created and edited from the web: `POST /api/orders`, `PATCH /api/orders/{id}`, an Add order form on Orders, and an Edit form on each order. SupplyGPT gained `create_order` and `update_order`, with the same rules as other actions. Pairs and grams must be in the quote. An order number is used only if the owner said it; otherwise the next SO number is assigned when the card is applied (the card says "next number, now SO-x"). Ship-by and yarn dates are resolved in code. Yarn per pair, if not said, is copied from the latest order and the card says so. Status is "tentative" for an enquiry or request, else "booked" (the model's judgement, shown on the card). An order without a yarn date is saved but not planned until one is given. New booked orders are planned ahead of tentative ones (D-21), so they can push tentative orders later. "Create, place, book an order" always means a new order, even for an existing buyer.
- D-61 "end of <month>", "end of this/the month" and "end of next month" resolve to that month's last day. "Mid August" or a bare month stays a question.

- D-62 Voice replies. After a voice message SupplyGPT speaks its reply (Sarvam `POST /text-to-speech`, `bulbul:v3`, speaker `kavya`, MP3 at 24 kHz, `enable_preprocessing`; set `SARVAM_TTS_MODEL` and `SARVAM_TTS_SPEAKER` in `.env` to change). Typed messages get a ▶ Play button, plus an optional "Read replies aloud" switch. What is spoken is built in code from the checked cards: "Waiting for your approval", one short sentence per pending change from its validated payload, any clarifying question, then "Approve or reject on the screen". The model's own reply is spoken only when there is no card, cut to two sentences, because live replies were long (over 30 s) and sometimes contradicted the cards. Dates are said as "15 June" with no year (a year scrambled the Tamil translation). The script goes through Sarvam translate for the owner's language, but **a translation that loses or changes any number is not spoken; the English is spoken instead**. Live, the Tamil translation silently dropped "2" from "2 of the knitting machines"; the wording "Knitting machines: 2 machines will not be working on 15 June" keeps every number in 3 of 3 runs. Verified live by round trip (speech, then Sarvam STT) in English and Tamil, and in the browser (autoplay, about 12 s real playback, play and stop). Approving by voice is not built: approval stays a click on the card.

- D-33 Fixture m1 is labelled `slips_vs_planned: true`, but its promise (cotton yarn, 2027-06-22) is earlier than SO-1182's planned yarn arrival (2027-06-25). The message says bales arrive on the 22nd and yarn will be "a few days late" after that. Code can't derive a slip from that date without a bales-to-yarn lead time. Not tested in M2; needs a rule (lead time, or treat the date as raw-material arrival) before M5 recomputes the plan. **Now visible in M5:** with the sample messages loaded, SO-1182's yarn date moves from Jun 25 (planned) to Jun 22 (promise). The order gains 3 days of resilience even though the supplier said yarn will be late. Under "yarn 4 days late" it shows Jul 20 (+0) instead of the golden Jul 31 (-11). The UI says the date came from a promise, and `use_promises=false` restores the golden numbers.
